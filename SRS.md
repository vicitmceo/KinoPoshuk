## 1. Вступ

### 1.1 Мета документа

Цей документ є єдиним джерелом правди щодо функціональних та нефункціональних
вимог до веб-застосунку "Кінопошук" на етапі курсового проєкту. Документ
використовується для затвердження теми проєкту викладачем та як базис для
планування розробки за методологією Scrum.

### 1.2 Область застосування продукту

"Кінопошук" — веб-застосунок для пошуку інформації про фільми за назвою, зі
збереженням обраних фільмів та історії пошуку. Користувач вводить назву
фільму, застосунок звертається до зовнішнього OMDb API і відображає картку
фільму: постер, рік випуску, режисера, акторський склад, жанр, тривалість,
рейтинг та короткий опис сюжету. Знайдений фільм можна додати в "Обране";
кожен пошуковий запит фіксується в "Історії" незалежно від результату.

### 1.3 Терміни та скорочення

| Термін | Опис |
|---|---|
| OMDb API | Open Movie Database — публічне REST API з даними про фільми |
| SRS | Software Requirements Specification |
| DTO | Data Transfer Object — об'єкт передачі даних між шарами |
| EF Core | Entity Framework Core — ORM для доступу до SQL Server |
| MVP | Minimum Viable Product |

## 2. Загальний опис

### 2.1 Архітектурна перспектива

Застосунок побудований за **Clean Architecture** (4 шари + SharedKernel) —
детальний опис і обґрунтування кожного шару в
[docs/architecture/ARCHITECTURE.md](docs/architecture/ARCHITECTURE.md) та
[docs/architecture/class-diagram.md](docs/architecture/class-diagram.md):

- **Presentation:** `Controllers/`, `Middleware/`, `wwwroot/` — HTTP-шар та статичний фронтенд
- **Application:** сервіс `MovieService`, DTO, мапери — бізнес-логіка
- **Domain:** сутності `FavoriteMovie`, `SearchHistoryEntry`, контракти репозиторіїв — без залежностей від інших шарів
- **Infrastructure:** `KinoPoshukDbContext` (EF Core → SQL Server), `OmdbApiClient` (зовнішнє API)
- **SharedKernel:** винятки, константи, розширення — спільні для всіх шарів

### 2.2 Класи користувачів

| Клас | Опис |
|---|---|
| Відвідувач | Будь-який користувач без реєстрації: пошук, перегляд і керування обраним, перегляд історії |

Реєстрація та розмежування прав у поточній версії не передбачені — обране
та історія спільні для всіх відвідувачів (немає поняття "акаунт").

### 2.3 Технічне середовище

- Backend: ASP.NET Core 9 Web API (Controllers, не Minimal API — див. ARCHITECTURE.md)
- База даних: SQL Server (LocalDB для розробки), доступ через EF Core 9
- Frontend: HTML5, CSS3, Vanilla JavaScript (Fetch API), 3 екрани (вкладки)
- Розгортання: локально (`dotnet run`) або хостинг ASP.NET Core сумісний з провайдером
- Підтримувані браузери: останні версії Chrome, Firefox, Edge

### 2.4 Технологічні обмеження

- Ліміт запитів OMDb API для безкоштовного ключа (1000 запитів/день)
- API-ключ зберігається лише на бекенді (`appsettings.json` → `Omdb:ApiKey`), не передається клієнту
- Потрібен доступний екземпляр SQL Server (LocalDB) для роботи "Обраного" й "Історії"

## 3. Межі проєкту

### In Scope (поточна ітерація, тиждень 1–2)

- Пошук фільму за точною або частковою назвою
- Відображення картки фільму з постером і метаданими
- Додавання фільму в "Обране" зі збереженням у SQL Server
- Перегляд і видалення записів з "Обраного"
- Автоматичний запис кожного пошукового запиту в "Історію" (знайдено/не знайдено)
- Перегляд останніх 20 записів історії
- Обробка помилок (фільм не знайдено, порожній запит, недоступність API, відсутній запис при видаленні)
- Стилізований інтерфейс з трьома вкладками (Пошук / Обране / Історія)

### Out of Scope (поточна ітерація)

- Реєстрація/авторизація користувачів (обране й історія — спільні, не персональні)
- Рекомендаційна система
- Мультимовність інтерфейсу (крім української)
- Кешування відповідей OMDb
- Пагінація результатів пошуку (OMDb `?t=` повертає один найрелевантніший фільм)

## 4. Функціональні вимоги

| ID | Вимога | Пріоритет (MoSCoW) | Критерій прийняття |
|---|---|---|---|
| FR-1 | Користувач вводить назву фільму в поле пошуку | Must | Поле вводу присутнє на вкладці "Пошук" |
| FR-2 | При натисканні "Пошук" застосунок надсилає запит на `GET /api/search?title=...` | Must | Запит виконується без перезавантаження сторінки |
| FR-3 | Бекенд проксіює запит до OMDb API з прихованим ключем | Must | Ключ API відсутній у клієнтському коді/мережевих запитах браузера |
| FR-4 | Результат відображається карткою: постер, назва, рік, режисер, актори, жанр, рейтинг, тривалість, опис | Must | Усі поля видимі при успішному пошуку |
| FR-5 | Якщо фільм не знайдено — показується повідомлення про помилку | Must | HTTP 404 + текст "Фільм не знайдено" |
| FR-6 | Порожній запит блокується на клієнті | Should | Кнопка "Пошук" не надсилає запит при порожньому полі |
| FR-7 | Пошук за натисканням Enter | Could | Поле вводу реагує на клавішу Enter так само, як кнопка |
| FR-8 | Кожен пошуковий запит (успішний і невдалий) записується в історію | Must | Новий рядок з'являється в `SearchHistoryEntries` після кожного `GET /api/search` |
| FR-9 | Користувач може додати знайдений фільм у "Обране" кнопкою "+ В обране" | Must | `POST /api/favorites` створює запис; повторне додавання того ж `ImdbId` не дублює запис |
| FR-10 | Вкладка "Обране" показує всі збережені фільми з постером, назвою, роком, датою додавання | Must | `GET /api/favorites` повертає список, що рендериться на сторінці |
| FR-11 | Користувач може видалити фільм з "Обраного" | Must | `DELETE /api/favorites/{id}` видаляє запис; повторний виклик повертає 404 |
| FR-12 | Вкладка "Історія" показує останні 20 пошукових запитів з позначкою знайдено/не знайдено | Must | `GET /api/history` повертає список, відсортований за часом (спадання) |
| FR-13 | Перемикання між вкладками не перезавантажує сторінку | Should | Дані вкладки підвантажуються через `fetch` при першому відкритті |

## 5. Use Cases

### UC-1: Успішний пошук фільму

1. Користувач відкриває головну сторінку (вкладка "Пошук")
2. Вводить назву фільму (напр. "Inception")
3. Натискає "Пошук"
4. Застосунок показує індикатор завантаження
5. Бекенд отримує дані з OMDb, паралельно записує запит в історію, повертає JSON
6. Frontend рендерить картку фільму з кнопкою "+ В обране"

**Постумова:** картка фільму відображена, запис з'явився в історії

### UC-2: Фільм не знайдено

1. Користувач вводить назву неіснуючого фільму
2. Бекенд не отримує даних від OMDb, записує в історію `WasFound = false`, повертає HTTP 404
3. Frontend показує повідомлення "Фільм не знайдено"

### UC-3: Недоступність OMDb API

1. Користувач виконує пошук під час недоступності зовнішнього API
2. `OmdbApiClient` кидає `ExternalApiException`, яку перехоплює `ExceptionHandlingMiddleware`
3. Бекенд повертає HTTP 502, Frontend показує повідомлення "Сервіс тимчасово недоступний"

### UC-4: Додавання фільму в обране

1. Користувач знаходить фільм (UC-1)
2. Натискає "+ В обране"
3. Frontend надсилає `POST /api/favorites` з даними фільму
4. `MovieService` перевіряє, чи вже є фільм з таким `ImdbId`; якщо ні — зберігає
5. Користувач переходить на вкладку "Обране" й бачить фільм у списку

### UC-5: Видалення фільму з обраного

1. Користувач відкриває вкладку "Обране"
2. Натискає "Видалити" біля фільму
3. Frontend надсилає `DELETE /api/favorites/{id}`
4. Якщо запис існує — видаляється, список оновлюється; якщо ні — `MovieNotFoundException` → HTTP 404

### UC-6: Перегляд історії пошуку

1. Користувач відкриває вкладку "Історія"
2. Frontend надсилає `GET /api/history`
3. Відображається список останніх 20 запитів з позначкою "знайдено"/"не знайдено" та часом

## 6. Нефункціональні вимоги

| Категорія | Вимога |
|---|---|
| Продуктивність | Відповідь на пошуковий запит — не довше 3 секунд за нормальних умов мережі |
| Надійність | Коректна обробка помилок зовнішнього API та БД без падіння застосунку (централізовано в `ExceptionHandlingMiddleware`) |
| Безпека | API-ключ OMDb зберігається в `appsettings.json`, не потрапляє у відповідь клієнту |
| Цілісність даних | Повторне додавання одного фільму в обране (той самий `ImdbId`) не створює дублікат |
| Юзабіліті | Інтерфейс українською мовою, зрозумілий без інструкцій; перемикання вкладок без перезавантаження |
| Доступність | Достатній контраст кольорів, читабельна типографіка |
| Спостережуваність | Кожен HTTP-запит логується (`RequestLoggingMiddleware`) з методом, шляхом, статусом і часом виконання |

## 7. Ризики

| Ризик | Імовірність | Вплив | Мітигація |
|---|---|---|---|
| Вичерпання денного ліміту OMDb API | Середня | Середній | Кешування останніх запитів — заплановано в наступній ітерації |
| Зміна структури відповіді OMDb API | Низька | Високий | Ізольовано в `OmdbApiClient`/`OmdbRawResponse` (Infrastructure) — зміна не торкнеться інших шарів |
| Недоступність SQL Server (LocalDB) при демонстрації | Середня | Високий | Міграція застосовується автоматично (`db.Database.Migrate()`), інструкція з розгортання в README |
| Відсутність реєстрації → спільне "Обране" для всіх відвідувачів | Висока (навмисне спрощення) | Низький на MVP-етапі | Явно задокументовано в Out of Scope, буде переглянуто з появою авторизації |

---

## 8. Метрики успіху

- Успішний пошук ≥ 95% валідних назв фільмів, наявних в OMDb
- Час відповіді інтерфейсу ≤ 3 сек
- Коректна обробка 100% помилкових сценаріїв (порожній запит, фільм не знайдено, недоступність API, видалення неіснуючого запису)
- 100% пошукових запитів фіксуються в історії незалежно від результату
